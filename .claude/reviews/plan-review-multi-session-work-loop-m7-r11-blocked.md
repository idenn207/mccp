Task 1 validation only checks syntactic normalization (C1-REGISTRY-PATH-NORMALIZED: 'absolute paths become repo-relative or <outside-repo>') but not whether the source value is appropriate. Plan DD4 states 'cited_path는 repo-relative로 정규화해 기록한다' but does not specify that emit points must restrict their inputs. This means a malicious or buggy emit point could pass arbitrary paths, which after normalization could obscure intent (e.g., passing '../../../../etc/passwd', normalized to '<outside-repo>', creating a finding that appears innocuous but could aid reconnaissance). |
| security | MEDIUM | Plan's `finding_id` is deterministic from normalized claim text, creating collision risk if normalization differs between write and read paths | Plan Task 1 specifies: 'finding_id는 (work_unit, gate_id, perspective, severity, normalizedClaim)의 sha256 앞 16자이고 normalizedClaim은 소문자화 + 공백 축약 + 구두점 제거 후 절단이다.' The plan does not specify: (1) truncation length for normalizedClaim, (2) whether claim_digest (a separate allowlist field capped at 256 chars) is identical to normalizedClaim or a truncated variant, (3) whether the hash input is pre-normalized or not. If normalizedClaim undergoes different truncation at write vs. in test fixtures, or if the implementation drifts from specification, two distinct findings could hash to the same finding_id, causing one to be silently deduped and lost (silently dropping half of a duplicate pair violates the append-only integrity model). Task 1 validation (C1-REGISTRY-APPEND) tests idempotent re-writes of same finding, but does not test hash collision scenarios or mismatched normalization lengths between writer and reader. |
| security | HIGH | Plan does not specify data origin validation for `cited_path` passed by emit points, allowing privilege escalation via false HIGH/CRITICAL findings pointing to unrelated code locations | Task 4 specifies three emit points but makes no statement about what cited_path value each may legitimately pass. For plan-codex-runner (Task 4.2), the plan says it reads 'Plan-Codex judgment' but does not specify whether findings from Codex can include arbitrary cited_path values or must reference only the plan file being reviewed. If Codex finding includes a claimed cited_path like 'some/arbitrary/file.js', the emit point will pass it through, normalization will accept it (as long as it's within repo), and a HIGH/CRITICAL finding will be escalated to the next session's work list (Task 5) pointing to code the user did not intend to review. This is a privilege escalation: Codex output defines which files appear in the work list for the next session. The plan's only defense (DD1: constant PROMOTE_MIN_SEVERITY='HIGH') does not prevent this - it only prevents LOW findings from escalating. A compromise of Codex responses or a Codex hallucination could create HIGH-severity findings pointing to arbitrary repo locations, forcing review of unrelated code. |
