# mccp v0.2 State File Schemas

> **Status**: reference-only. Schemas are enforced by code in
> `plugins/mccp/scripts/state/` and `plugins/mccp/scripts/lib/`. This file
> is the human-readable contract — when the format drifts, this file is
> the authority used to reconcile.

All v0.2 state lives under `<repo>/.claude/state/`. Per plan §4 `.gitignore`
row, only the bounded-counter and advisory-lock files are gitignored;
`STATE.md` and `fix-task.md` are **git-tracked** so context survives
worktree resets and pair-programming handoffs (Reviewer B Round 1 #9).

```
.claude/state/
├── STATE.md                       # session-bridging context (git-tracked)
├── fix-task.md                    # current pending fix task (git-tracked)
├── fix-task-applied.md            # rotated copy after SessionStart inject (git-tracked)
├── loop-counter.json              # per-task bounded counters (gitignored)
├── *.lock                         # advisory locks (gitignored)
└── handoff-lock-<repoHash>.lock   # spawner race lock, 5min TTL (gitignored)
```

The repo's `.gitignore` lists `.claude/state/loop-counter.json` and
`.claude/state/*.lock` to keep ephemeral artifacts out of commits.

## 1. `STATE.md` — session-bridging context

Written by `state/state-writer.js` on PreCompact. Injected by
`state/state-injector.js` on SessionStart.

### Frontmatter

```yaml
---
state_version: 1
task_fingerprint: <sha256-hex-first-12>
created_at: <ISO-8601-UTC>
updated_at: <ISO-8601-UTC>
last_event: stop_loop_pass | receipt_write | pr_created | fix_task_applied | precompact
last_event_at: <ISO-8601-UTC>
unsafe_checkpoint: true | false
confirm_required: true | false        # user Q1 opt-in for SessionStart confirm
next_chunk: |                          # optional, see §1.2
  <multi-line markdown chunk for next session>
---
```

Required keys: `state_version`, `task_fingerprint`, `created_at`,
`updated_at`. Missing required keys → injector skips with warning
(Risk #3 mitigation).

### Body sections (templated — writer enforces order and bounds)

```markdown
## Goal
<= 3 lines summarizing the active task

## Plan
- <plan path 1>
- <plan path 2>

## Done
- <checked-off task>
- <checked-off task>

## In Progress
- <current task with status>

## Next Step
<single line — what the next session should do first>

## Last Decision
<single paragraph — most recent decision worth carrying forward>

## Open Questions
- HIGH: <question>
- MEDIUM: <question>
- LOW: <question>

## Last Updated
<ISO-8601-UTC>
```

Free-form writing is rejected — writer always uses this template. Sections
must appear in this order. Each section's line bound is enforced by the
writer (Goal ≤3, Next Step =1, Last Decision =1 paragraph, etc.).

### 1.2 `next_chunk` (auto-handoff Sprint 10b)

When breakpoint-detector triggers a soft or hard handoff, the writer
populates `next_chunk` with a markdown chunk the injector replays as the
first user-prompt in the spawned session.

For hard ceilings ($100 USD), `next_chunk` begins with the pending
fix-task content (verbatim from `fix-task.md`), so the next session
tackles the fix before resuming general work (user Q8 — hard ceiling
override of fix-task-first policy).

`confirm_required: true` makes the injector emit a single "이어가시겠습니까?"
prompt before replaying the chunk. Default `false` per user request to
minimize friction.

### 1.3 Writer-driven events and injector skip matrix

The `last_event` enum is populated by `state/state-writer.js update()` whenever
a wiring point invokes it. Current wiring (v0.2 — S10a):

| Event | Trigger | Hook / caller |
|---|---|---|
| `precompact` | PreCompact hook fires | `scripts/hooks/pre-compact.js` |
| `stop_loop_pass` | Stop-loop quality runner returns clean | (v0.3 wiring — writer API ready) |
| `receipt_write` | receipt CLI `write` succeeds | (v0.3 wiring — writer API ready) |
| `pr_created` | `/mccp:pr` completes successfully | (v0.3 wiring — writer API ready) |
| `fix_task_applied` | injector consumes pending fix-task | (v0.3 wiring — writer API ready) |

Unknown event values are downgraded to `precompact` with a stderr warning so a
caller misspelling an event cannot corrupt downstream consumers.

The injector (`state/state-injector.js inject()`) is failure-isolated — a
problem reading STATE.md never blocks fix-task replay and vice versa. The
matrix for the two files:

| STATE.md status | fix-task.md status | Injector behavior |
|---|---|---|
| missing | missing | empty stdout, exit 0 |
| missing | present | fix-task body returned in stdout (rotation deferred — see "consume-vs-deliver" below) |
| valid (version 1, all keys) | missing | STATE.md only |
| valid | present | STATE.md first, then fix-task body (rotation deferred) |
| unsupported `state_version` | * | STATE skipped with stderr warning, fix-task path proceeds normally |
| missing required frontmatter key | * | STATE skipped with stderr warning, fix-task path proceeds normally |
| no frontmatter / corrupt | * | STATE skipped with stderr warning, fix-task path proceeds normally |

Lazy 7-day sweep: at every SessionStart, the injector checks
`fix-task-applied.md`'s mtime. If older than 7 days, it is unlinked before any
inject decision (Risk #6 — wallclock drift is out-of-scope for v0.2).

`confirm_required: true` is consulted only when STATE.md injection succeeded;
the prompt is appended after both system-reminder blocks (so the user reads
both STATE.md and fix-task before answering).

**Consume-vs-deliver contract** (Codex stop-time review, S10a): `inject()`
is read-only with respect to `fix-task.md`. It returns the body but does
not rotate. The caller (`scripts/hooks/session-start.js`) must call
`commitFixTaskApplied(repoRoot)` only **after** the additionalContext
payload has been successfully flushed to the session frontend. This makes
inject-and-deliver an at-least-once cycle: if Claude Code drops the payload
or the stdout write throws, the pending `fix-task.md` survives and the next
SessionStart re-delivers it. `commitFixTaskApplied()` is idempotent —
calling it on a repo with no pending fix-task is a no-op.

**Partial-delivery guard via paired sentinels** (Codex stop-time review,
S10a follow-up): the formatted fix-task block is wrapped with two unique
markers — `FIX_TASK_HEAD_MARKER` immediately after the opening
`<system-reminder>` and `FIX_TASK_TAIL_MARKER` on its own line just before
the closing `</system-reminder>`. `limitSessionStartContext()` is a hard
prefix slice (it truncates at `MCCP_SESSION_START_MAX_CHARS` and appends a
notice), so a cut anywhere inside the body keeps the HEAD but discards the
TAIL. The SessionStart guard therefore requires **both** markers to be
present in the post-truncation `additionalContext` before calling
`commitFixTaskApplied`. Head-only checks accept a mid-body slice as
"delivered" and rotate the file even though the user only saw half of it,
which violates the at-least-once contract above. Both markers are exported
from `state-injector.js` so no caller has to duplicate the literal string.

## 2. `fix-task.md` — Stop-loop failure → next-turn correction

Written by `state/fix-task.js` after the Stop-loop's quality runner (or
optional Codex bridge) returns a fail/divergent/critical verdict.
Replayed by `state/state-injector.js` as a `<system-reminder>` on the
next session start. Once applied, renamed to `fix-task-applied.md` to
prevent stale re-application.

### Frontmatter

```yaml
---
fix_task_version: 1
task_fingerprint: <sha256-hex-first-12>
gate_id: stop-review-loop
decision_id: <see §5 cross-gate dedupe key>
created_at: <ISO-8601-UTC>
expires_at: <ISO-8601-UTC>           # created_at + 7 days (user Q4)
counter: <int 1..2>                   # current loop counter value
verdict: quality_fail | codex_divergent | codex_critical
escalate: true | false                # dual-reviewer escalation flag
originating_receipts:
  - <decision-id of plan-codex>
  - <decision-id of implement-codex>
---
```

### Body sections

```markdown
## Title
<one-line summary of the failure>

## Why
<2-3 lines: which gate failed and what the fix-task is meant to
re-trigger on the next turn>

## Failures
- <stage>: <exit code> | <one-line excerpt>
- <stage>: <exit code> | <one-line excerpt>

## Next Actions
1. <imperative action — e.g. "Re-run npm run lint and fix...">
2. <imperative action>

## Originating Decisions
- gate: <gate_id>, decision: <decision_id>, receipt: <path>

## Dual Reviewer Escalation Required        # only if escalate: true
Next: run /santa-loop "<original-prompt>"
```

Expiration: `fix-task-applied.md` is swept after 7 days (user Q4). Sweep
runs lazily — at SessionStart, the injector deletes any
`fix-task-applied.md` older than `now - 7 days`.

## 3. `loop-counter.json` — per-task bounded counter

Written by `state/loop-counter.js`. Read by `hooks/stop-review-loop.js`
before invoking the quality runner. Atomic rename (Risk #2 mitigation).

```json
{
  "version": 1,
  "tasks": {
    "<task_fingerprint>": {
      "count": 0,
      "lastAt": "<ISO-8601-UTC>",
      "fixTaskHash": "<sha256-hex-first-12 of last fix-task.md body>"
    }
  }
}
```

### Rules

- `count = 0` → first Stop-loop pass for this task.
- `count = 1` → Stop-loop fired once, failed, fix-task issued.
- `count = 2` → Stop-loop fired twice and still failing. Hook emits
  "human-takeover" meta and **allows** the response through (avoids
  infinite block loop, brainstorming pain ① mitigation).
- `count > 2` → never reached (counter capped at 2 in writer).

### `task_fingerprint` derivation

```
task_fingerprint = sha256(first 200 chars of first user prompt of current session).hex.slice(0, 12)
```

The 12-hex prefix collision risk is acceptable for a session-local
counter — at 5 entries/session the birthday-attack probability is
< 1e-9.

### Concurrency

The counter file is read-modify-write. Concurrent Stop hooks (rare but
possible with parallel sub-agent runs) must coordinate via atomic
rename (`*.<pid>.<random>.tmp` → final), same pattern as
`scripts/lib/session-bridge.js writeBridgeAtomic`. Corrupt JSON →
counter reset to `{version:1, tasks:{}}` + stderr warning.

## 4. `handoff-lock-<repoHash>.lock` — spawner race lock

Written by `state/session-spawner.js` immediately before invoking the
spawn command (tmux / Start-Process). Format:

```
<pid>\n<iso-8601-utc>\n<repoHash>\n
```

TTL: 5 minutes. Spawner reads the lock first; if `now - lock_ts < 5min`,
spawn is skipped and falls back to notify. After 5 minutes, the lock
is considered stale and overwritten.

`<repoHash>` = `sha256(repo-root-path).hex.slice(0, 12)`. Multi-worktree
isolation: each worktree has its own lock file, so handoffs from one
worktree never block another's spawn (user Q7).

## 4.5 `pr-phase-lock-stale-reclaimed.json` — orphan-lock audit marker (v1.0.1 axis K)

State-file marker dropped by `scripts/hooks/pr-phase-guard.js` `lockActive()`
when it reclaims an orphan `pr-phase.lock` (same-host + dead PID). Converts
silent recovery into a loud audit trail: `scripts/lib/pr-phase-helpers/finalize-receipt.js`
reads the marker on the next PR cycle, unlinks it, and forwards
`--pr-phase-lock-stale-reclaimed-at-hook` to the receipt CLI, which stamps
`meta.pr_phase_lock_stale_reclaimed_at_hook=true` on the next PR receipt.

**Path**: `<root>/.claude/state/pr-phase-lock-stale-reclaimed.json`

**Body shape**:

```json
{
  "reclaimed_at": "<ISO-8601 UTC>",
  "former_run_id": "<uuid of the orphan lock's run_id, or null>",
  "former_pid": <int>,
  "former_host": "<hostname>",
  "reason": "same-host-dead-pid"
}
```

**Writer**: `pr-phase-guard.js writeStaleReclaimMarker()` — atomic via tmp+rename, mode 0o600, path-containment-guarded (`assertContained(markerDir, <root>/.claude)`).

**Reader**: `finalize-receipt.js consumeStaleReclaimMarker()` — read + unlink (best-effort). Corrupt-but-present markers still count as "audit fact consumed" so a parse error doesn't suppress the audit; the unlink still happens so a corrupt marker doesn't stick.

**Lifetime**: written when guard reclaims an orphan lock, deleted on the next finalize-receipt invocation (the next PR cycle's Phase 2.5.6). If two reclaims happen between PR cycles (rare — implies double crash), the second overwrites the first (latest wins; tested by axis 12.2).

**Idempotency**: marker absence is the normal state. `consumeStaleReclaimMarker()` returns false on ENOENT without emitting noise. Multiple finalize-receipt invocations in a single session are safe — only the first consumes; subsequent calls no-op.

**Sealed-channel invariant (F11)**: this marker is **token-free** and **audit-only** — it does NOT carry any part of the F11 ownership-token contract. The `pr-phase.lock` body's `ownership_token_hash` schema is untouched by axis K (zero schema-diff invariant in the v1.0.1 plan's Acceptance row 4). The marker is a separate state file with its own purpose; finalize-receipt reads it without touching the lock body at all.

## 5. Cross-gate dedupe key — Reviewer A A5 contract

> **Reviewer A A5 gating (Risk #18)**: This is the load-bearing key
> that lets plan-codex, implement-codex, and stop-loop-codex agree on
> "the same decision is being reviewed". Without it, Codex reviews
> double-fire (cost waste) or skip incorrectly (review gap).

### Function signature

`scripts/state/dedupe-key.js`:

```javascript
/**
 * Derive a normalized cross-gate dedupe key.
 *
 * @param {string} planPath              - Absolute or repo-relative plan/PRD path
 *                                          (or empty string for branch-based commands)
 * @param {string} decisionId            - decision_id from receipt or hook input
 * @returns {string}                     - 24-hex key: sha256(planSha12 + ':' + slug).slice(0,24)
 */
function dedupeKey(planPath, decisionId)
```

### Matching rules

Two gate invocations are considered "the same decision" if and only if
their `dedupeKey(planPath, decisionId)` outputs are equal. The function
performs:

1. **Plan path normalization** — absolute path resolved, then converted
   to repo-relative (relative to `git rev-parse --show-toplevel`).
   Forward-slash normalized. Empty string if no plan path (branch-based
   commands like `/mccp:pr`).
2. **`planSha12`** — `sha256(normalized planPath).hex.slice(0, 12)`. For
   empty plan path, `planSha12 = '000000000000'`.
3. **Decision slug normalization** — lowercase, replace runs of
   non-`[a-z0-9-]` with `-`, strip leading/trailing `-`, truncate to 80.
   Trims conventional branch prefixes (`feat/`, `fix/`, etc.) before
   normalization to match the receipt CLI's `slugFromBranch` behavior.
4. **Key derivation** — `sha256(planSha12 + ':' + normalized_slug).hex.slice(0, 24)`.

The 24-hex output is the dedupe key. It is **deterministic** (no clocks,
no env, no randomness), so plan-codex's key written at planning time
matches stop-loop-codex's key derived months later from the same plan
path and decision slug.

### Why both plan path AND decision slug

- `decisionId` alone collides across plans (two unrelated PRDs both
  default to `slugFromBranch` = current branch).
- `planPath` alone collides across decisions within one plan (same plan
  file, different `--decision` slug for two branches).
- The composite `planSha12 + ':' + slug` matches the receipt CLI's
  decision-derivation precedence exactly:

| `derivedecisionId` precedence | dedupeKey input |
|---|---|
| 1. explicit `--decision <slug>` | `(planPath, '<slug>')` |
| 2. PLAN_PATH_COMMANDS → slugFromPlanArg | `(planPath, slug-from-plan-arg)` |
| 3. BRANCH_BASED_COMMANDS → slugFromBranch | `('', branch-slug)` |
| 4. `'default'` fallback | `(planPath || '', 'default')` |

### Receipt → dedupe key reverse lookup

Given an existing receipt at `<repo>/.claude/receipts/<gate>/<decision_id>.json`,
extract its dedupe key by:

```javascript
const receipt = JSON.parse(fs.readFileSync(receiptPath, 'utf8'));
const key = dedupeKey(receipt.subject.plan_path || '', receipt.decision_id);
```

`receipt.subject.plan_path` is populated by the receipt CLI when the
`--plan <path>` argument was provided, and `null` otherwise (which
collapses to the empty-plan-path branch above).

### Usage

- **plan-codex** writes `key` into receipt metadata as
  `receipt.meta.dedupe_key`.
- **implement-codex** reads plan-codex receipt, computes its own key
  from the implementation's plan path + decision_id, and skips Codex
  invocation if keys match (Cross-gate dedupe, Risk #4).
- **stop-loop-codex** (when `MCCP_STOP_LOOP_CODEX=1`) checks **both**
  plan-codex and implement-codex receipts. If either receipt's key
  matches the current Stop event's derived key, the Codex bridge is
  skipped and the quality runner result alone is used.

### Test fixtures (Task 4b)

- `same plan path + same decision_id → same key`
- `same plan path + different decision_id → different key`
- `different plan path + same decision_id → different key`
- `branch-based command (no plan path) → planSha12 = 000000000000`
- `feat/foo branch slug normalizes to 'foo'`
- `windows backslashes normalize to forward-slash`
- `absolute and relative paths to same file produce same key`

## 6. Schema versioning

All v0.2 state files carry a `*_version: 1` key (`state_version`,
`fix_task_version`, `"version": 1` for JSON). Bumps follow semver
intent:

- **Backward-compatible additions** (new optional sections, new
  optional frontmatter keys) — no version bump.
- **Renames or removed required keys** — version bump, injector skips
  unsupported versions with a warning and clears the state file.

v0.2 ships at version 1. v0.3 may bump to 2 if `/mccp:work` adds
single-flow automation context that needs cross-session persistence.
