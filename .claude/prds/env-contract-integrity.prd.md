# 환경변수 계약 무결성과 온보딩 표면

## Problem

mccp 운영자가 환경변수를 설정하면 **그 값이 선언대로 동작하지 않는 경우가 있고, 동작하지 않았다는 사실을 알 방법이 없다.** 계약(레지스트리 + 문서)과 실제 동작이 어긋나는 지점이 다섯 층에 걸쳐 있는데, 오늘 존재하는 검사(lint 9종)는 **계약 내부의 정합만** 보므로 다섯 층 중 어느 것도 보지 못한다. 그래서 lint는 green을 보고하면서 운영자는 물린다.

방치 비용은 이미 실현됐다. 다른 프로젝트에서 mccp를 실사용하던 중 세 건이 연달아 발생해 작업이 지연되고 리소스가 추가 소모됐으며, 그중 하나는 게이트 교착으로 이어졌다. 그리고 이 문제는 **자기 은폐적**이다 — 값이 무시되는 방식이 조용하므로, 운영자는 자신이 무엇을 설정했다고 믿은 채로 다른 원인을 찾는다.

## Evidence

실사용 3건(운영자 직접 보고, 2026-08-21) — 전부 코드 대조로 재확인됨:

- **`MCCP_DISABLED_HOOKS`의 절반이 조용히 무효였다.** 설정한 두 id 중 하나가 등록된 29개에 존재하지 않는 이름이었는데, 파서는 미상 토큰을 **검증도 경고도 없이 수용**한다. 운영자는 두 개를 껐다고 믿었고 하나만 꺼졌다. 값은 ECC 문서를 보고 넣은 것이며(mccp는 ECC fork), mccp의 정답은 같은 레지스트리 안의 다른 토글이었으나 발견될 경로가 없었다.
- **`MCCP_REVIEW_SINGLE_PASS=deadline_pressure`인데 15라운드 이상 진행됐다.** `/mccp:plan`과 `/mccp:prp-implement` 양쪽에서 관측. 판정 오라클은 정확히 `cap=1, pinned=true`를 돌려주고 두 명령 본문이 그 오라클을 실제로 호출하지만, **라운드 루프 자체가 LLM이 읽는 산문**이라 초과를 막는 장치가 없다. 15는 선언된 모든 캡(게이트 3, santa 10)을 넘는다.
- **`MCCP_CODEX_DISABLED=1`을 전역 설정에 넣고 세션을 재시작했는데 plan과 PR에서 Codex가 호출됐다.** 체크 지점 8곳이 모두 공유 파서를 거치며 로직은 정상이다. 8곳이 동시에 틀릴 수 없으므로 **값이 프로세스에 도달하지 않았다**는 것이 유일한 정합적 설명이다. 이어서 Codex를 강제로 막자 receipt가 작성되지 않아 implement가 게이트에 막히는 **교착**이 발생했다 — 즉 정상 우회 경로가 실패해 운영자를 구조적으로 막히는 경로로 밀어냈다.

메타 조사 2건(2026-08-20) — 실측 기반:

- [env-contract-behavior-drift](../_meta/2026-08-20-env-contract-behavior-drift.md) — 문서가 가르치는 값이 코드에 없는 토글 **9건**(최악: `MCCP_PLAN_REVIEW=off`가 리뷰를 끄는 대신 Codex 리뷰를 켠다), 셸 bool 계약 위반 3건, kind 오기 5건, evidence 포인터 드리프트 **98/161**, enum 27개 중 **15개**가 값의 뜻을 문서 어디에도 갖지 않음, list **9개 전부** 멤버 어휘 0개, 레지스트리 밖에서 동작하는 게이트 토글 5건.
- [env-settings-authoring-surface](../_meta/2026-08-20-env-settings-authoring-surface.md) — 계약 정보가 세 곳으로 투영되지만 **운영자 손끝에 닿는 것이 0개**. 운영자의 실제 설정 파일을 검사하는 장치가 없음. 그리고 온보딩 walkthrough를 데이터 수리 전에 켜면 잘못된 값을 **모든 신규 사용자에게 권위 있는 객관식으로 제시**하게 되어 잠재 결함이 능동적 오교육으로 전환됨.

관찰된 다섯 층 — 각 층마다 오늘 검사가 없다:

| 층 | 무엇이 어긋나는가 |
|---|---|
| A | 계약이 선언한 값 ↔ 코드가 실제로 받는 값 |
| B | 코드가 아는 사실 ↔ 운영자가 설정을 쓰는 지점 |
| C | 판정 오라클 ↔ 실제 강제 (오라클이 맞아도 소비처가 산문이면 안 지켜짐) |
| D | 설정 파일의 선언 ↔ 프로세스가 실제로 받은 값 |
| E | 코드 변경 ↔ 문서 갱신 (사람의 기억에 의존) |

## Users

- **Primary**: mccp를 실제 작업에 쓰는 운영자. 특히 (a) 신규 설치 직후로 어떤 토글이 존재하는지 모르는 사용자, (b) 게이트가 막히거나 비용이 튀어 원인을 환경변수에서 찾아야 하는 사용자, (c) ECC 사용 경험을 가지고 넘어와 ECC 패턴을 그대로 적용하는 사용자.
- mccp 설계자 본인도 여기 포함된다 — 각 토글의 역할을 완전히 파악하지 못한 상태라고 직접 밝혔다. 저자가 모르면 사용자는 확실히 모른다.
- **Not for**: 161개 전부를 튜닝하려는 파워유저. 그 사용자는 상세 문서를 직접 읽으며, 이 PRD의 온보딩 축은 그를 대상으로 하지 않는다.

## Hypothesis

We believe **환경변수 계약을 코드에서 파생시키고, 계약과 실제 동작의 일치를 기계적으로 검사하며, 운영자의 실제 설정이 프로세스에 도달했는지 확인 가능하게 만드는 것**이
will **"설정했는데 동작하지 않고 알 방법도 없다"를 해소** for **mccp를 실사용하는 운영자**.

We'll know we're right when **운영자가 명령 하나로 자신의 설정이 선언대로 도달했는지 확인할 수 있고, 계약과 코드가 어긋난 상태가 착지 전에 차단되며, 실사용에서 보고된 세 유형의 물림이 재발하지 않을 때**.

## Scope

**MVP** — 계약과 코드의 어긋남을 착지 전에 막는 검사, 그리고 운영자가 **자신의 설정이 선언대로 프로세스에 도달했는지** 확인하는 진단. 진단은 설정 파일이 *선언한 값*과 프로세스가 *실제로 받은 값*을 나란히 놓는다. 이 둘만으로 다섯 층 중 A·B·D를 덮고, 실사용 3건 중 2건이 즉시 진단 가능해진다.

**Out of scope**

- **온보딩 walkthrough · 에디터 스키마 · 전용 열람 페이지** — 데이터가 정확해지기 전에 켜면 잘못된 값을 신규 사용자에게 권위 있게 가르치는 장치가 된다. 같은 PRD의 뒤쪽 마일스톤이며 MVP가 아니다.
- **`MCCP_PLAN_REVIEW`의 "리뷰 없음" 모드를 실제로 구현하는 것** — 승인 없이 진행한 기록을 무엇으로 봉인할지가 함께 정해져야 하는 별개 판단이다. 최소 수리는 존재하지 않는 값을 계약에서 제거하는 쪽이다.
- **evidence 포인터 98건 일괄 재생성** — 소비처가 여럿인 토글에서 무엇을 대표로 삼을지의 규칙이 없다.
- **레지스트리 밖 토글의 은퇴** — ECC 상속 이름의 하위 호환 판단이 필요하다.
- **진단을 게이트로 편입하는 것** — 게이트 추가는 별도 판정이 필요하며 이 PRD는 권하지도 반대하지도 않는다.
- **Claude Code 본체의 설정 병합 동작을 바꾸는 것** — 통제 밖이다. 이 PRD는 그 동작을 *관측 가능하게* 만들 뿐이다.
